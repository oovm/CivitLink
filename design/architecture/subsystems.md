# 三大子系统的元设计

元引擎由三个核心子系统组成：元编译器、元编辑器和元运行时。这些子系统共同构成了一个完整的引擎生成与运行体系。

## 1. 元编译器架构

编译器不再是针对单一语言的简单前端+后端，而是**图重写系统**与**多级中间表示**的流水线。

### 1.1 统一资产处理图

元编译器核心是一个**有向无环图（DAG）调度器**，图中的每个节点都是一个**转换器**。转换器实现标准接口：

```
(inputs: ArtifactSet, context: BuildContext) -> outputs: ArtifactSet
```

转换器可以是内置的（纹理压缩、着色器编译），也可以是引擎清单中指定的插件。例如：

- `script_compiler`：读取`.v` Valkyrie 脚本，产出`StorySequence`资产和`DialogueDB`。
- `rpg_map_compiler`：读取`.tilemap`与事件定义，产出碰撞网格、寻路数据与序列化的事件触发器。
- `platform_aot_backend`：将**引擎通用字节码**（见下文）转换为目标平台原生代码。

### 1.2 逻辑脚本的AOT与JIT双模策略

元引擎定义了一种**低级可移植字节码**（例如基于WebAssembly的扩展子集，或自定义的寄存器式IR）。该字节码具有以下特性：

- **紧凑**，适合热更新传输。
- **类型明确**，允许AOT编译成高效原生代码。
- **支持调试符号映射**，以便在编辑器中实现源码级断点和HMR。

脚本语言（如Lua、TypeScript、自定义行为树）通过**语言前端转换器**编译为这种字节码。在**开发模式**下，运行时使用**字节码解释器**（或轻量级JIT），以支持HMR（替换单个函数/模块）。在**发布构建**时，编译器流水线会调用目标平台的AOT后端（例如通过LLVM或Cranelift）将字节码连同引擎本身编译为单一可执行文件。

这种设计让同一份游戏逻辑可以**无缝在编辑器的即时预览（解释执行）和最终高性能发行版（AOT执行）之间切换**，且保持行为一致。

## 2. 元编辑器设计

元编辑器本身是一个**壳程序（Shell）**，不包含任何特定游戏类型的UI。它加载引擎清单，然后动态组装工作区。

### 2.1 编辑器即插件平台

编辑器使用**微内核+服务插件**架构：

- **核心壳**：提供窗口管理、命令分发、撤销/重做栈、资产数据库同步、HMR客户端。
- **工作区插件**：由引擎清单指定，例如：
  - **场景视图**：可能是瓦片地图编辑器（RPG/横板）或分镜树视图（Galgame）。
  - **属性检查器**：根据GOM Schema动态生成。
  - **脚本IDE集成**：与语言服务器协议（LSP）集成，提供代码补全、类型提示（类型信息由编译器生成的符号数据库提供）。
  - **调试与性能面板**：显示实体层级、逻辑流追踪、GPU/CPU分析。

### 2.2 即时模式预览与HMR调试

编辑器不直接"运行游戏"，而是启动一个**附着式的运行时实例**（可以是独立进程，也可以是编辑器进程内隔离的沙盒）。二者之间通过**调试线缆（Debug Wire）** 通信。

**热模块替换（HMR）流程**：

1. 开发者在编辑器中修改脚本、材质、或GOM组件属性。
2. 编辑器内的**资产监视器**触发**增量编译流水线**（仅重新编译受影响的转换器节点）。
3. 新生成的字节码/资产通过调试线缆推送到运行时。
4. 运行时执行**状态迁移**：
   - 如果是纯资源（纹理、音频），直接替换GPU/内存对象。
   - 如果是脚本函数，运行时利用字节码的**版本化热替换表**，将当前游戏状态的执行上下文迁移到新函数入口（要求GOM Schema支持状态序列化与重载钩子）。
5. 游戏世界继续运行，开发者在编辑器中立即看到修改效果，无需重启。

这种HMR不仅适用于脚本，理论上也适用于**引擎代码本身**（如果引擎以动态库形式加载，且状态可序列化），但通常只开放到脚本与资产层以确保稳定性。

## 3. 元运行时设计

运行时是游戏最终执行的容器，但它是**高度模块化**的，体现了 Rust 和 Valkyrie 的明确分工。

### 3.1 核心宿主抽象层（HAL）- Rust 实现

定义一组**服务特征（Traits/Interfaces）**，由 Rust 实现：

- `Renderer`：接受`DrawCommand`队列（2D精灵、Tile图层、文字等）。
- `AudioEngine`：播放声音、控制混音。
- `InputSource`：键盘、鼠标、触摸、手柄统一抽象。
- `FileSystem`：资产加载，支持从压缩包、网络流或Mod文件夹透明读取。

HAL的实现是**可互换**的。例如同一个运行时核心，可以在PC上使用Vulkan后端，在Web上使用WebGL后端，但上层游戏逻辑（GOM + 脚本）完全一致。

### 3.2 游戏模式与系统调度

运行时核心包含一个**系统调度器**（Rust实现），它根据引擎类型激活不同的**功能组**：

- **Galgame模式**：激活命令解释器、对话历史栈、立绘动画系统。ECS可能退化为一个轻量级状态机。
- **RPG/横板过关模式**：激活完整的**Entity-Component-System（ECS）** 框架。元引擎的ECS实现允许**系统（System）作为插件注册**。

### 3.3 语言分工在运行时的体现

- **Rust 负责**：HAL实现、系统调度器、ECS核心、性能关键系统
- **Valkyrie 负责**：游戏逻辑、事件处理、Mod内容、UI逻辑

这种运行时结构天然支持**Mod**：Mod文件实际上是一个**增量资源包** + **增量脚本字节码**（Valkyrie）。运行时启动时，按优先级合并基础游戏资产与Mod资产，覆盖GOM组件值或添加新实体。Mod甚至可以注册新的系统（例如新的UI或玩法机制），前提是这些系统遵守运行时安全接口。
