# 架构概览

本项目是一个元游戏引擎框架，定位为编译时框架，通过插件组合机制生成具体的游戏引擎，支持多平台分发。在诺斯替（Gnostic）宇宙观的隐喻下，**太一（gg）** 是超越的源头，**德穆革（具体游戏引擎）** 是有限的世界造物主，**执权者（游戏创造者）** 管理各自的世界，共同构建一个可扩展的游戏创造宇宙。

> 关于 Gnostic 神话隐喻的详细解释，请参考 [Gnostic 架构文档](/gnostic/overview)。

### 各层次职责

#### 1. 元引擎框架（太一）
- **ECS核心**：万物生成的基始，一切实体与关系的雏形
- **资源抽象**：未成形的原质（如影像、音声），等待被赋予形式
- **虚拟机（gg）**：灵性知识得以传播的媒介，包含 Valkyrie 脚本系统
- **平台抽象层**：太一的"遍在性"，使其能显现于不同物质载体
- **插件注册与组合机制**：流溢的通道

#### 2. 具体游戏引擎（德穆革）
- 由资深玩家使用元引擎框架，选择一组插件静态编译而成
- 包含 GG Editor（跨平台 GUI 开发框架）和运行时模式（世界法则）
- 每位德穆革拥有固定的能力范围（如Galgame、STG、横版闯关）

#### 3. 游戏实例（游戏世界）
- **编辑端**：灵性蓝图，执权者在此进行创造，使用 GG Editor 开发 GUI 界面
- **运行时客户端**：物质显现，玩家直接体验的世界，包含原生 GUI 界面
- **服务器端**（可选）：宇宙法则，维持多人世界的真实性与连续性

### 平台抽象层职责

平台抽象层屏蔽操作系统和运行环境的差异，为上层提供统一接口，包含以下子模块：

- **文件系统抽象**：统一接口访问各平台存储
- **输入抽象**：统一处理按键、鼠标/触摸、游戏手柄等事件
- **渲染抽象**：基于 `wgpu` 统一图形渲染（游戏渲染）
- **GUI 抽象**：统一处理各平台原生 GUI 系统（GUI 渲染）
- **音频抽象**：统一播放控制，支持常见格式
- **时间与线程抽象**：统一获取系统时间、休眠、线程生成
- **动态链接与虚拟机支持**：确保 gg 虚拟机能在目标平台运行

### 各平台分发形态

| 平台        | 分发形式                                    | 说明                                                                 |
| ----------- | ------------------------------------------- | -------------------------------------------------------------------- |
| Windows     | `.exe` 安装程序或便携版                     | 包含所有插件和运行时，可独立运行                                   |

## 项目整体结构：Cargo Workspace 设计

项目采用 Cargo Workspace 结构，按功能分组组织模块：

- **core/**: 核心抽象与基础类型，包括共享数据结构、错误类型、HAL 接口定义、ECS 核心实现和统一资产处理框架
- **compiler/**: 编译器相关模块，包括编译流水线图调度器、转换器 trait、脚本语言前端、AOT 编译后端、*.vx 文件编译器和可移植字节码定义/解释器
- **editor/**: 跨平台 GUI 开发框架，包括 GUI 框架核心、GUI 编译器、GUI 运行时、基础 GUI 组件库和可视化 GUI 设计器
- **runtime/**: 运行时相关模块，包括系统调度器、宿主服务接口、HMR 状态迁移、渲染后端抽象、GUI 运行时抽象、音频后端抽象和脚本运行时（包含 Valkyrie 脚本系统）
- **platforms/**: 平台特定胶水层，包括 Windows/macOS/Linux、WebAssembly/WebGL 和 iOS/Android（预留）
- **plugins/**: 官方提供的领域专用插件模块，包括视觉小说/对话系统插件、瓦片地图与碰撞插件、Spine 骨骼动画支持和通用 UI 系统
- **examples/**: 示例，展示如何使用 gg 引擎定制各环节

    游戏运行时 <-->|双向通信| ModDLC
    引擎清单解析器 -->|解析| 代码与配置生成器

**依赖关系核心原则**：

- 上层（工厂生成的编辑器/运行时）只依赖**基础模块**和**选定插件**。
- 基础模块之间通过**trait 抽象**解耦（例如 `gg-runtime-gfx` 依赖 `gg-core` 定义的 `Renderer` trait，而非具体后端）。
- 官方插件必须实现 `gg-core` 中对应的 `Plugin` trait，以便被引擎工厂动态加载和组合。

## 元引擎的组合生成机制：引擎工厂

### 引擎清单（Engine Manifest）

每个由元引擎生成的游戏引擎实例都由一个**声明式配置文件**定义，我们称之为**引擎清单**。该清单包含：

- **基础元数据**：名称、版本、目标游戏类型。
- **模块选取**：
  - 游戏对象模型模块（例如 `GOM.VisualNovel` 或 `GOM.ARPG`）。
  - 脚本运行时模块（例如 `VM.Lua` 或 `VM.Wasm` 或 `VM.BehaviorTree`）。
  - 渲染前端模块（例如 `Render.SpriteStack` 或 `Render.Immediate2D`）。
- **工具链扩展点**：声明编译器中需要启用的自定义处理步骤、编辑器中需要加载的面板与视图。
- **平台AOT后端列表**：例如 `windows-x64`, `web-wasm`, `android-arm64`。

元引擎的**引擎工厂**读取此清单，动态生成三个产物：

1. **定制编译器**（命令行工具或库）。
2. **定制编辑器**（IDE的插件包或独立应用骨架）。
3. **定制运行时**（一组静态库与引导代码）。

开发者也可以在此基础上进行**增量修改**——清单本身也支持继承与补丁，从而快速从"横板过关引擎"变种出"类银河城特化引擎"。

### 游戏对象模型的元描述

元引擎最关键的部分是**GOM Schema**——用一种与语言无关的接口定义语言（类似Protobuf/FlatBuffers + 行为标注）描述游戏世界中的实体、组件、事件与系统。

例如，对于RPG引擎，GOM可能包含：

```
entity Player {
  components: [Transform, Health, Inventory, SkillSet]
}

entity NPC {
  components: [Transform, DialogueTree, Vendor]
}
```

元编译器根据GOM Schema自动生成：
- 类型安全的C++/Rust/TypeScript数据结构（用于运行时和编辑器）。
- 序列化/反序列化代码（用于存档、网络同步、热重载状态迁移）。
- 编辑器的属性面板与资源选择器UI片段。
- 脚本绑定代码（用于Lua/Wasm与核心引擎交互）。

因此，**定义GOM就是定义一半的游戏引擎**。元引擎提供了高度可扩展的GOM编辑器，允许引擎开发者可视化地设计组件、事件流，并自动获得编辑器和运行时的支持。

## GG Editor - 跨平台 GUI 开发框架

### 定位与目标

GG Editor 重新定位为跨平台 GUI 开发框架，主要用于编辑器界面的开发，采用原生渲染方式以获得更好的性能和原生体验。游戏内的 UI（如游戏菜单、HUD 等）仍使用 WGPU 自渲，确保与游戏渲染的一致性和性能。

### *.vx 文件格式

GG Editor 使用类似 Vue 的 *.vx 文件格式，包含三个部分：

1. **<template>**：使用 TSX 语法，支持 Layout、Stack 等基础组件
   ```tsx
   <Layout style="tailwind">
     <Stack></Stack>
   </Layout>
   ```

2. **<script>**：使用 Valkyrie 脚本语法，类似 SolidJS 的响应式编程模型
   ```javascript
   // Valkyrie grammar, like solidjs
   ```

3. **<style>**：使用 SCSS 语法，但由 GG Renderer 渲染，不需要支持所有 SCSS 特性
   ```scss
   /* scss grammar */
   ```

### 架构组成

1. **编译器**：将 *.vx 文件编译为平台特定的 GUI 代码
   - 解析 *.vx 文件结构
   - 编译 <template> 部分为平台特定的 GUI 代码
   - 编译 <script> 部分为 Valkyrie 脚本
   - 编译 <style> 部分为 GG Renderer 可处理的样式

2. **运行时**：跨平台 GUI 运行时，支持在各大平台上以原生形式运行
   - 平台抽象层：处理不同平台原生 GUI 系统的差异
   - 原生 GUI 渲染：使用各平台的原生 GUI 系统
   - 与游戏引擎集成：与 ECS 架构无缝集成

3. **编辑器**：可视化编辑 *.vx 文件
   - 语法高亮和代码提示
   - 实时预览
   - 热更新支持

### 跨平台支持

GG Editor 支持在以下平台上以原生形式运行：
- Windows
- macOS
- iOS
- Android
- H5
- 微信小游戏

### 与游戏引擎的集成

GG Editor 与游戏引擎的 ECS 架构无缝集成，GUI 系统可以：
- 访问游戏世界的实体和组件
- 响应游戏事件
- 触发游戏逻辑

## 设计原则

### 1. ECS作为统一核心

借鉴Unity的DOTS架构，所有游戏逻辑最终都通过ECS系统执行，确保性能和数据驱动。ECS世界提供统一的实体、组件、系统模型，所有插件和Mod都基于此模型交互。

### 2. WASM作为脚本虚拟机

类似于Godot的GDExtension，但更安全、跨平台。脚本在沙箱中运行，不能直接访问内存。通过导入函数暴露ECS API，确保安全可控。

### 3. 插件化架构

参考Unreal的模块系统，每个功能模块独立编译，引擎构建时静态链接，保证运行时性能。插件之间通过ECS世界通信，实现松耦合。

### 4. 平台抽象层

借鉴Godot的跨平台设计，通过trait抽象各平台差异，上层代码无需关心底层实现。平台抽象层包含文件系统、输入、渲染、GUI、音频、时间与线程等子模块。

### 5. 两层monorepo结构

避免目录过深，同时保持模块清晰。`crates/`下按功能领域划分，每个领域内部再按具体模块细分。

### 6. 静态与动态分离

- 编译时：元引擎框架 + 插件组合 → 生成具体引擎可执行文件
- 运行时：游戏数据包 + DLC/Mod → 动态加载，无需重新编译引擎

### 7. 不同层次玩家各司其职

- **普通玩家**：通过配置数据和编写剧本（DLC）就能创作游戏，无需编程
- **高级玩家**：使用虚拟机脚本（gg）编写Mod，实现更复杂的自定义逻辑
- **资深玩家**：基于元引擎框架开发新的引擎插件或全新引擎（Rust代码），静态编译后发布

## 总结

通过Gnostic神话的透镜，gg元引擎架构展现出深层的象征结构：太一作为超越源头，德穆革作为有限造物主，执权者作为世界管理者，玩家作为灵性寻求者。每一层都既独立又相连，共同构成一个可扩展、跨平台的游戏创造宇宙。

这种架构实现了"不同层次玩家各司其职"的目标，同时确保了：
- 高性能：核心逻辑使用Rust静态编译
- 跨平台：平台抽象层屏蔽差异
- 可扩展：插件机制和Mod脚本提供灵活性
- 热更新：HMR支持运行时内容迭代

无论你是先知（引擎开发者）、执权者（游戏设计师）还是寻求灵知的玩家（Mod作者），都能在这个框架中找到自己的位置。
