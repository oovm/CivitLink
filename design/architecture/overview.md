# 架构概览

本项目是一个元游戏引擎框架，定位为编译时框架，通过插件组合机制生成具体的游戏引擎，支持多平台分发。在诺斯替（Gnostic）宇宙观的隐喻下，**太一（gg）** 是超越的源头，**德穆革（具体游戏引擎）** 是有限的世界造物主，**执权者（游戏创造者）** 管理各自的世界，共同构建一个可扩展的游戏创造宇宙。

> 关于 Gnostic 神话隐喻的详细解释，请参考 [Gnostic 架构文档](/gnostic/overview)。

## 元引擎作为编译时框架的总体架构

元引擎框架采用静态与动态分离的设计思想，分为三个层次，对应诺斯替神话中的三层宇宙结构：

```mermaid
graph TD
    A[元引擎框架 (编译时) 太一（The One）]
    B[具体游戏引擎 (静态可执行文件) 德穆革（Demiurge）]
    C[游戏实例 (运行时) 物质世界（Kosmos）+ 普累若麻（Pleroma）]
    
    A -->|资深玩家选择插件，编译生成具体引擎| B
    B -->|普通/高级玩家创作内容，动态加载| C
    
    subgraph A1[元引擎框架组件]
        A1_1[ECS核心]
        A1_2[资源系统]
        A1_3[虚拟机 gg]
        A1_4[插件注册与组合机制]
    end
    
    subgraph B1[具体游戏引擎组件]
        B1_1[Galgame插件 静态链接]
        B1_2[STG插件 静态链接]
        B1_3[Game UI System 插件 静态链接]
        B1_4[内置编辑器（可选）]
        B1_5[运行时（ECS调度器）]
    end
    
    subgraph C1[游戏实例组件]
        C1_1[游戏项目（由DLC/Mod构成）]
        C1_2[引擎配置文件]
        C1_3[资源包]
        C1_4[DLC内容]
        C1_5[Mod脚本]
        C1_6[HMR补丁（实时更新）]
    end
    
    C1_1 --> C1_2
    C1_1 --> C1_3
    C1_1 --> C1_4
    C1_1 --> C1_5
```

### 各层次职责

#### 1. 元引擎框架（太一）

- **ECS核心**：万物生成的基始，一切实体与关系的雏形
- **资源抽象**：未成形的原质（如影像、音声），等待被赋予形式
- **虚拟机（Valkyrie）**：灵性知识得以传播的媒介，包含 Valkyrie 脚本系统
- **平台抽象层**：太一的"遍在性"，使其能显现于不同物质载体
- **插件注册与组合机制**：流溢的通道

#### 2. 具体游戏引擎（德穆革）

- 由资深玩家使用元引擎框架，选择一组插件静态编译而成
- 包含 GG Editor（跨平台 GUI 开发框架）和运行时模式（世界法则）
- 每位德穆革拥有固定的能力范围（如Galgame、STG、横版闯关）

#### 3. 游戏实例（游戏世界）

- **编辑端**：灵性蓝图，执权者在此进行创造，使用 GG Editor 开发 GUI 界面
- **运行时客户端**：物质显现，玩家直接体验的世界，包含原生 GUI 界面
- **服务器端**（可选）：宇宙法则，维持多人世界的真实性与连续性

## 运行时与多平台分发架构

在已有静态编译框架基础上，增加平台抽象层和构建/分发策略，确保引擎能适配 Windows、macOS、iOS、Android、H5、微信小游戏等主要平台：

```mermaid
graph TD

    B[具体游戏引擎 (多平台构建)]
    C[游戏实例 (运行时)]
    
    A -->|针对目标平台静态链接插件，生成引擎可执行文件| B
    B -->|游戏数据包 + DLC/Mod 跨平台分发| C
    
    subgraph A1[元引擎框架组件]
        A1_1[ECS核心]
        A1_2[资源系统]
        A1_3[虚拟机 gg]
        A1_4[平台抽象层]
        A1_5[插件组合与构建工具链 多目标支持]
    end
    
    subgraph B1[具体游戏引擎组件]
        B1_1[Windows引擎 .exe]
        B1_2[macOS引擎 .app/dmg]
        B1_3[iOS引擎 .ipa]
        B1_4[Android引擎 .apk/aab]
        B1_5[H5引擎 WASM+HTML]
        B1_6[微信小游戏引擎 WASM+小游戏适配]
    end
    
    subgraph C1[游戏实例组件]
        C1_1[游戏数据包（剧本、资源、配置）]
        C1_2[DLC内容（增量数据）]
        C1_3[Mod脚本（Valkyrie代码，需虚拟机执行）]
        C1_4[HMR开发支持（可选，平台限定）]
    end
```

### 平台抽象层职责

平台抽象层屏蔽操作系统和运行环境的差异，为上层提供统一接口，包含以下子模块：

- **文件系统抽象**：统一接口访问各平台存储
- **输入抽象**：统一处理按键、鼠标/触摸、游戏手柄等事件
- **渲染抽象**：基于 `wgpu` 统一图形渲染，服务游戏渲染和 Game UI System（Canvas + GPU 渲染）
- **GUI 抽象**：仅服务 Editor UI Toolkit，处理各平台原生 GUI 系统差异（独立渲染器）
- **音频抽象**：统一播放控制，支持常见格式
- **时间与线程抽象**：统一获取系统时间、休眠、线程生成
- **动态链接与虚拟机支持**：确保 gg 虚拟机能在目标平台运行

### 各平台分发形态

| 平台      | 分发形式                              | 说明                                          |
| ------- | --------------------------------- | ------------------------------------------- |
| Windows | `.exe` 安装程序或便携版                   | 包含所有插件和运行时，可独立运行                            |
| macOS   | `.app` 或 `.dmg`                   | 需签名以通过 Gatekeeper                           |
| iOS     | `.ipa`（通过 TestFlight 或 App Store） | 需 Apple 开发者证书；游戏数据包需通过 iTunes 文件共享或 App 内下载 |
| Android | `.apk` 或 `.aab`（Google Play）      | 需签名；支持外部存储读取游戏数据包                           |
| H5      | 静态文件（HTML + JS + WASM）            | 部署在 Web 服务器上，通过浏览器访问                        |
| 微信小游戏   | 小游戏代码包（包含 WASM 和适配层 JS）           | 需通过微信小游戏审核，遵循小游戏规范                          |

## 项目整体结构：Cargo Workspace 设计

项目采用 Cargo Workspace 结构，按功能分组组织模块：

- **core/**: 核心抽象与基础类型，包括共享数据结构、错误类型、HAL 接口定义、ECS 核心实现和统一资产处理框架
- **compiler/**: 编译器相关模块，包括编译流水线图调度器、转换器 trait、脚本语言前端、AOT 编译后端、\*.widget 文件编译器和可移植字节码定义/解释器
- **editor/**: Editor UI Toolkit，包括 GUI 框架核心、GUI 编译器、GUI 运行时、基础 GUI 组件库和可视化 GUI 设计器，仅用于编辑器界面开发
- **runtime/**: 运行时相关模块，包括系统调度器、宿主服务接口、HMR 状态迁移、渲染后端抽象、GUI 运行时抽象、音频后端抽象和脚本运行时（包含 Valkyrie 脚本系统）
- **platforms/**: 平台特定胶水层，包括 Windows/macOS/Linux、WebAssembly/WebGL 和 iOS/Android（预留）
- **plugins/**: 官方提供的领域专用插件模块，包括视觉小说/对话系统插件、瓦片地图与碰撞插件、Spine 骨骼动画支持和 Game UI System（游戏运行时 UI，基于 ECS + Canvas 体系）
- **examples/**: 示例，展示如何使用 gg 引擎定制各环节

以下是用 mermaid 绘制的架构层次图，展示了从**元引擎工厂**到**具体游戏**的生成关系与模块依赖：

        A1_1b[Game UI System + *.gameui 文件支持（游戏运行时 UI）]
        A1_2[游戏运行时 gg-runtime-core + 领域系统]
        A1_3[Mod / DLC 沙盒 VM + 资产覆盖层]
    end
    
    subgraph B1[元引擎工厂组件]
        B1_1[引擎清单解析器]
        B1_2[代码与配置生成器]
    end
    
    subgraph C1[引擎基础模块层组件]
        C1_1[核心模块]
        C1_2[功能模块]

    A1_2 <-->|双向通信| A1_3

**依赖关系核心原则**：

- 上层（工厂生成的编辑器/运行时）只依赖**基础模块**和**选定插件**。
- 基础模块之间通过**trait 抽象**解耦（例如 `gg-runtime-gfx` 依赖 `gg-core` 定义的 `Renderer` trait，而非具体后端）。
- 官方插件必须实现 `gg-core` 中对应的 `Plugin` trait，以便被引擎工厂动态加载和组合。

## 元引擎的组合生成机制：引擎工厂

### 引擎清单（Engine Manifest）

每个由元引擎生成的游戏引擎实例都由一个**声明式配置文件**定义，我们称之为**引擎清单**。该清单包含：

- **基础元数据**：名称、版本、目标游戏类型。
- **模块选取**：
  - 游戏对象模型模块（例如 `GOM.VisualNovel` 或 `GOM.ARPG`）。
  - 脚本运行时模块（例如 `VM.Lua` 或 `VM.Wasm` 或 `VM.BehaviorTree`）。
  - 渲染前端模块（例如 `Render.SpriteStack` 或 `Render.Immediate2D`）。
- **工具链扩展点**：声明编译器中需要启用的自定义处理步骤、编辑器中需要加载的面板与视图。
- **平台AOT后端列表**：例如 `windows-x64`, `web-wasm`, `android-arm64`。

元引擎的**引擎工厂**读取此清单，动态生成三个产物：

1. **定制编译器**（命令行工具或库）。
2. **定制编辑器**（IDE的插件包或独立应用骨架）。
3. **定制运行时**（一组静态库与引导代码）。

开发者也可以在此基础上进行**增量修改**——清单本身也支持继承与补丁，从而快速从"横板过关引擎"变种出"类银河城特化引擎"。

### 游戏对象模型的元描述

元引擎最关键的部分是**GOM Schema**——用一种与语言无关的接口定义语言（类似Protobuf/FlatBuffers + 行为标注）描述游戏世界中的实体、组件、事件与系统。

例如，对于RPG引擎，GOM可能包含：

```
entity Player {
  components: [Transform, Health, Inventory, SkillSet]
}

entity NPC {
  components: [Transform, DialogueTree, Vendor]
}
```

元编译器根据GOM Schema自动生成：

- 类型安全的C++/Rust/TypeScript数据结构（用于运行时和编辑器）。
- 序列化/反序列化代码（用于存档、网络同步、热重载状态迁移）。
- 编辑器的属性面板与资源选择器UI片段。
- 脚本绑定代码（用于Lua/Wasm与核心引擎交互）。

因此，**定义GOM就是定义一半的游戏引擎**。元引擎提供了高度可扩展的GOM编辑器，允许引擎开发者可视化地设计组件、事件流，并自动获得编辑器和运行时的支持。

## GG Editor UI Toolkit

### 定位与目标

GG Editor UI Toolkit 是 GG Editor 专用的声明式 UI 框架，基于文档对象模型（DOM），借鉴 Web 前端设计理念，仅用于编辑器界面开发。它拥有独立渲染器，直接在图形设备层上工作，默认绘制在游戏画面最上层。游戏内的 UI（如游戏菜单、HUD 等）使用独立的 Game UI System，基于 ECS + Canvas 体系，确保与游戏渲染的一致性和对 3D 空间 UI、着色器特效的支持。

### \*.widget 文件格式

GG Editor 使用类似 Vue 的 \*.widget 文件格式，包含三个部分：

1. **<template>**：使用 TSX 语法，支持 Layout、Stack 等基础组件
   ```tsx
   <Layout style="tailwind">
     <Stack></Stack>
   </Layout>
   ```
2. **<script>**：使用 Valkyrie 脚本语法，类似 SolidJS 的响应式编程模型
   ```javascript
   // Valkyrie grammar, like solidjs
   ```
3. **<style>**：使用 SCSS 语法，但由 GG Renderer 渲染，不需要支持所有 SCSS 特性
   ```scss
   /* scss grammar */
   ```

### 架构组成

1. **编译器**：编译 *.widget 文件为 Editor UI Toolkit 的平台特定代码
   - 解析 *.widget 文件结构
   - 编译 <template> 部分为平台特定的 GUI 代码
   - 编译 <script> 部分为 Valkyrie 脚本
   - 编译 <style> 部分为 GG Renderer 可处理的样式
2. **运行时**：Editor UI 运行时，仅用于编辑器 UI 渲染
   - 平台抽象层：处理不同平台原生 GUI 系统的差异
   - 原生 GUI 渲染：使用各平台的原生 GUI 系统（仅针对编辑器 UI）
   - 与游戏引擎集成：与 ECS 架构无缝集成
3. **编辑器**：可视化编辑 *.widget 文件
   - 语法高亮和代码提示
   - 实时预览
   - 热更新支持

### 跨平台支持

GG Editor 支持在以下平台上以原生形式运行：

- Windows
- macOS
- iOS
- Android
- H5
- 微信小游戏

### 与游戏引擎的集成

GG Editor 与游戏引擎的 ECS 架构无缝集成，GUI 系统可以：

- 访问游戏世界的实体和组件
- 响应游戏事件
- 触发游戏逻辑

## Game UI System - 游戏运行时 UI 系统

### 定位与目标

Game UI System 是游戏运行时专用的 UI 框架，基于 ECS/GameObject 体系，类似 Unity uGUI。每个 UI 元素（按钮、图片、文字等）都是一个 Entity，挂载着 UiCanvas、UiImage、UiText 等组件，完全遵循 ECS 工作流。所有 UI 元素必须在 UiCanvas 组件下，Canvas 负责批量处理并提交给 GPU 渲染。

### 核心特性

- **基于 ECS**：UI 元素作为 Entity 存在于 ECS 世界中，可响应游戏事件，与游戏逻辑无缝集成
- **Canvas 管理**：Canvas 负责批量处理 UI 元素并提交给 GPU 渲染，支持 Batch 合批优化
- **3D 空间融合**：Canvas 可设置为 WorldSpace 模式，让 UI 像普通 3D 物体一样存在于游戏世界中（角色头顶血条、VR/AR 界面等）
- **着色器支持**：UI 元素可通过 UiMaterial 引用 *.shader 文件，支持特效、动画和后处理
- **动画系统**：与 *.animation 文件集成，支持 UI 元素的变换动画、颜色动画和自定义属性动画

### *.prefab 文件格式

Game UI System 使用 *.prefab 文件格式（RON 格式），包含 Canvas 配置、Entity 层级、UI 组件属性和着色器引用。详见 [Game UI 文件格式规范](/formats/gameui)。

### Canvas 渲染模式

| 模式 | 描述 | 适用场景 |
|------|------|---------|
| ScreenSpace | UI 绘制在屏幕最上层，不随相机移动 | 游戏 HUD、主菜单 |
| WorldSpace | UI 存在于 3D 世界中，像普通 3D 物体 | 角色头顶血条、VR/AR 界面 |
| CameraSpace | UI 跟随相机但保持固定距离 | 准星、提示信息 |

### 与 Editor UI Toolkit 的边界

| 对比维度 | Editor UI Toolkit (*.widget) | Game UI System (*.prefab) |
|---------|-------------------------|--------------------------|
| 用途 | 编辑器界面 | 游戏运行时 UI |
| 技术体系 | DOM 模型，声明式 | ECS/GameObject，组件式 |
| 渲染方式 | 独立渲染器 | Canvas + GPU 渲染 |
| 样式管理 | USS 样式系统 | 组件内联属性 |
| 3D 空间 | 不支持 | 支持 WorldSpace 模式 |
| 着色器 | 不支持 | 支持 UiMaterial |
| 动画 | CSS 过渡 | *.animation 动画系统 |

## 设计原则

### 1. ECS作为统一核心

借鉴Unity的DOTS架构，所有游戏逻辑最终都通过ECS系统执行，确保性能和数据驱动。ECS世界提供统一的实体、组件、系统模型，所有插件和Mod都基于此模型交互。

### 2. 明确的语言分工

**Rust 语言职责：**
- 构建游戏引擎核心，提供原生能力
- 与平台直接交互，处理底层系统
- 实现性能关键部分，如渲染、物理、资源管理
- 构建编译时框架和平台抽象层
- 提供安全、高效的底层实现

**Valkyrie 语言职责：**
- 处理所有游戏逻辑，包括游戏状态、AI行为、事件处理
- 通过 hook 式接口与引擎交互，类似 Godot、Unreal、Unity、Cocos
- 实现游戏系统、UI逻辑、Mod和DLC内容
- 支持热更新和动态内容扩展
- 提供灵活、易用的游戏开发环境

### 3. Valkyrie 脚本作为脚本虚拟机

类似于Godot的GDExtension，但更安全、跨平台。脚本在沙箱中运行，不能直接访问内存。通过导入函数暴露ECS API，确保安全可控。WASM/WASI 已降级为运行时，不再作为主要的脚本虚拟机。

### 4. 插件化架构

参考Unreal的模块系统，每个功能模块独立编译，引擎构建时静态链接，保证运行时性能。插件通过 Valkyrie 脚本实现，插件之间通过ECS世界通信，实现松耦合。

### 5. 平台抽象层

借鉴Godot的跨平台设计，通过trait抽象各平台差异，上层代码无需关心底层实现。平台抽象层包含文件系统、输入、渲染、GUI、音频、时间与线程等子模块。

### 6. 静态与动态分离

- **编译时（Rust）**：元引擎框架 + 插件组合 → 生成具体引擎可执行文件
- **运行时（Valkyrie）**：游戏数据包 + DLC/Mod → 动态加载，无需重新编译引擎

### 7. 不同层次玩家各司其职

- **普通玩家**：通过配置数据和编写剧本（DLC）就能创作游戏，无需编程
- **高级玩家**：使用虚拟机脚本（Valkyrie）编写Mod，实现更复杂的自定义逻辑
- **资深玩家**：基于元引擎框架开发新的引擎插件或全新引擎（Rust代码），静态编译后发布

## 总结

通过Gnostic神话的透镜，gg元引擎架构展现出深层的象征结构：太一作为超越源头，德穆革作为有限造物主，执权者作为世界管理者，玩家作为灵性寻求者。每一层都既独立又相连，共同构成一个可扩展、跨平台的游戏创造宇宙。

**核心设计理念：明确的语言分工**

- **Rust** 作为引擎核心语言，负责与平台交互，提供原生能力，处理性能关键部分，确保安全高效的底层实现
- **Valkyrie** 作为游戏逻辑语言，通过 hook 式接口与引擎交互，处理所有游戏逻辑，支持热更新和动态内容扩展

这种架构实现了"不同层次玩家各司其职"的目标，同时确保了：

- **高性能**：核心逻辑使用Rust静态编译
- **跨平台**：平台抽象层屏蔽差异
- **可扩展**：插件机制和Mod脚本提供灵活性
- **热更新**：HMR支持运行时内容迭代
- **开发友好**：Valkyrie提供灵活易用的游戏开发环境

无论你是先知（引擎开发者，使用Rust）、执权者（游戏设计师，使用Valkyrie）还是寻求灵知的玩家（Mod作者，使用Valkyrie），都能在这个框架中找到自己的位置。

通过这种明确的语言分工，GG游戏引擎既保证了底层的性能和稳定性，又提供了上层的灵活性和开发效率，为游戏开发提供了一个理想的平台。
