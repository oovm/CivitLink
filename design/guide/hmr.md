# 热更新与热模块替换（HMR）原理

## 概述

GG 游戏引擎提供两套互补的热更新机制，分别针对不同的使用场景：

- **Release 热更新**：面向最终用户的生产环境，支持游戏内容（剧本、资源、配置）的增量更新
- **Debug HMR**：面向开发者的开发环境，支持脚本和资源的实时热重载，加速创作迭代

## 1. Release 热更新

### 1.1 设计目标

Release 热更新旨在为最终用户提供无需重新下载完整游戏的增量更新能力，主要用于：

- 发布游戏补丁，修复 bug
- 增量更新游戏内容（新增章节、角色、剧情）
- 远程推送活动内容
- A/B 测试不同游戏内容

### 1.2 架构设计

```
┌─────────────────────────────────────────────────────────┐
│                    游戏数据包 (.pak)                      │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐       │
│  │ 剧本文件    │ │ 资源文件    │ │ 配置文件    │       │
│  │ *.v        │ │ *.png/wav   │ │ *.json      │       │
│  └─────────────┘ └─────────────┘ └─────────────┘       │
└─────────────────────────────────────────────────────────┘
                          │
                          │ 增量更新（差分包）
                          ▼
┌─────────────────────────────────────────────────────────┐
│                    远程更新服务器                         │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐       │
│  │ 版本目录    │ │ 差分包存储  │ │ 校验文件    │       │
│  │ manifest    │ │ deltas/     │ │ checksums   │       │
│  └─────────────┘ └─────────────┘ └─────────────┘       │
└─────────────────────────────────────────────────────────┘
```

### 1.3 核心机制

#### 1.3.1 版本管理

每个游戏数据包包含一个清单文件（manifest），记录当前版本的元信息：

```json
{
    "version": "1.2.0",
    "build_id": "20240115_abc123",
    "resources": {
        "scripts/game.v": {
            "hash": "sha256:abc123...",
            "size": 4096
        },
        "images/character.png": {
            "hash": "sha256:def456...",
            "size": 102400
        }
    }
}
```

#### 1.3.2 增量更新流程

```
1. 启动时检查版本
   └─> 请求远程服务器获取最新版本信息
       └─> 比较版本号和资源哈希
           ├─> 版本一致：直接启动
           └─> 有更新：下载差分包

2. 下载差分包
   └─> 计算需要下载的文件列表
       └─> 下载增量文件（bsdiff/bspatch）
           └─> 校验文件完整性

3. 应用更新
   └─> 备份当前版本资源
       └─> 合并差分包到资源目录
           └─> 更新本地 manifest
               └─> 启动游戏
```

#### 1.3.3 回滚机制

为防止更新失败导致游戏损坏，实现以下保护机制：

- **双目录结构**：维护 `current/` 和 `backup/` 两个资源目录
- **原子更新**：先更新 backup，成功后切换 current 指向
- **校验机制**：启动前校验所有资源文件完整性

### 1.4 更新策略

#### 全量更新 vs 增量更新

| 策略 | 适用场景 | 优势 | 劣势 |
|-----|---------|-----|-----|
| 全量更新 | 版本跨度大、网络不稳定 | 简单可靠 | 浪费流量 |
| 增量更新 | 版本连续、小更新 | 节省流量 | 实现复杂 |

#### 更新时机

- **启动时更新**：确保玩家始终使用最新版本
- **后台更新**：游戏运行时后台下载，下次启动生效
- **强制更新**：关键 bug 修复必须更新后才能游戏

### 1.5 安全考虑

- **HTTPS 传输**：防止中间人攻击
- **文件签名**：使用非对称加密验证文件完整性
- **白名单机制**：只允许更新特定目录下的文件
- **沙盒隔离**：更新过程不影响游戏主进程

## 2. Debug HMR（热模块替换）

### 2.1 设计目标

Debug HMR 旨在提升开发效率，实现以下目标：

- 修改脚本后无需重启游戏即可生效
- 修改资源后实时预览效果
- 保持游戏运行时状态，只替换变更部分
- 支持复杂的状态迁移，最小化对开发流程的影响

### 2.2 架构设计

```
┌─────────────────────────────────────────────────────────┐
│                      开发工具链                            │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐       │

│  └─────────────┘ └─────────────┘ └─────────────┘       │
│          │              │              │                │
│          └──────────────┴──────────────┘                │
│                         │ 文件变更                       │
│                         ▼                               │
│  ┌─────────────────────────────────────────────────┐ │
│  │              文件监视器 (File Watcher)             │ │
│  │  - inotify (Linux)                               │ │
│  │  - FSEvents (macOS)                              │ │
│  │  - ReadDirectoryChangesW (Windows)               │ │
│  └─────────────────────────────────────────────────┘ │
│                         │                             │

│                         │                             │

│  │              游戏运行时 (Runtime)                 │ │
│  │  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ │
```

### 2.3 核心机制

#### 2.3.1 HMR 事件类型

```rust
/// HMR 事件枚举
#[derive(Debug, Clone)]
pub enum HmrEvent {
    /// 脚本文件变更
    ScriptChanged {
        module_name: String,
        new_module: BytecodeModule,
    },
    /// 资源文件变更
    AssetChanged {
        asset_path: String,
        new_data: Vec<u8>,
    },
}
```

#### 2.3.2 HMR 管理器

HMR 管理器负责协调热替换的各个阶段：

```rust
pub struct HmrManager {
    /// 待处理的事件队列
    pending_events: Vec<HmrEvent>,
    /// 是否有脚本变更待处理
    script_dirty: bool,
    /// 是否有资源变更待处理
    asset_dirty: bool,
    /// 上一次成功加载的脚本模块（用于回滚）
    last_stable_module: Option<BytecodeModule>,
    /// 已变更的资源路径列表
    changed_assets: Vec<String>,
}
```

#### 2.3.3 热替换流程

```
1. 文件变更检测
   └─> 文件监视器检测到文件修改
       └─> 发送 HmrEvent 到事件队列

2. 事件处理（每帧检查）
   └─> Runtime.tick() 调用 HmrManager
       ├─> process_script_reload() 处理脚本变更
       │   └─> 重新编译脚本为字节码
       │
       └─> process_asset_reload() 处理资源变更
           └─> 重新加载资源文件

3. 状态迁移
   ├─> 脚本热替换：
   │   └─> 调用脚本的 on_hot_reload_in() 函数
   │       └─> 如返回成功，确认替换
   │       └─> 如返回失败，回滚到旧模块
   │
   └─> 资源热替换：
       └─> 更新资源缓存
           └─> 通知相关系统刷新显示

4. 开发者反馈
   └─> 在编辑器中显示替换结果
       ├─> 成功：绿色提示
       └─> 失败：红色错误 + 回滚提示
```

### 2.4 状态迁移策略

热替换最大的挑战是如何在保持游戏状态的同时应用变更。GG 引擎采用以下策略：

#### 2.4.1 脚本状态迁移

脚本状态包括全局变量、函数闭包等。HMR 管理器提供两种迁移策略：

**策略一：完整重置**

```rust
// 适用于全局状态简单的脚本
function on_hot_reload_in() {
    // 清理旧状态
    reset_global_state();
    // 初始化新状态
    init_state();
}
```

**策略二：增量迁移**

```rust
// 适用于需要保持状态的复杂脚本
function on_hot_reload_in(old_module) {
    // 从旧模块获取需要保留的状态
    let player_pos = old_module.get_global("player_pos");
    // 应用到新模块
    set_global("player_pos", player_pos);
}
```

#### 2.4.2 组件状态迁移

对于 ECS 组件，HMR 系统提供以下钩子：

```rust
/// 组件热更新钩子 trait
pub trait ComponentHmrHook {
    /// 热更新前调用，返回需要保存的数据
    fn before_hot_reload(&self) -> SerializableState;

    /// 热更新后调用，恢复保存的数据
    fn after_hot_reload(&mut self, state: SerializableState);
}
```

### 2.5 平台支持

| 平台 | 文件监视 | 通信机制 | 备注 |
|-----|---------|---------|-----|
| Windows | `ReadDirectoryChangesW` | 命名管道 | 原生 API |
| macOS | FSEvents | Unix Domain Socket | 原生 API |
| Linux | inotify | Unix Domain Socket | 内核接口 |
| iOS | FSEvents | Mach Port | 受限沙盒 |
| Android | inotify | ADB + TCP | 调试模式 |
| Web | 文件选择 API | WebSocket | 仅开发工具 |

### 2.6 性能考虑

HMR 过程中需要最小化对游戏性能的影响：

- **异步文件读取**：不阻塞主线程
- **增量编译**：只编译变更的模块
- **延迟应用**：在帧间隙应用变更
- **内存优化**：复用字节码内存，避免频繁分配

## 3. Release vs Debug 对比

| 特性 | Release 热更新 | Debug HMR |
|-----|---------------|-----------|
| **目标用户** | 最终玩家 | 开发者 |
| **更新内容** | 剧本、资源、配置 | 脚本、资源、配置 |
| **更新粒度** | 文件级别 | 模块级别 |
| **状态保持** | 不可保持（重新启动） | 尽量保持 |
| **网络要求** | 需要网络连接 | 本地文件监视 |
| **性能影响** | 更新时无影响 | 轻微帧率波动 |
| **回滚机制** | 支持版本回滚 | 支持即时回滚 |
| **安全要求** | 签名验证、校验 | 开发环境无需 |

## 4. 未来优化方向

- **差异编译**：只编译变更的函数，减少编译时间
- **预加载热补丁**：在游戏运行时预编译可能的变更
- **智能状态迁移**：基于代码分析自动推断状态迁移策略
- **协作编辑**：多人同时编辑时的冲突处理
